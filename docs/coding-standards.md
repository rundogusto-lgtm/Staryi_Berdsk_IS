# Стандарты кодирования проекта «Старый Бердск»

## Именование

- Переменные и параметры: camelCase — `objectId`, `bookingDate`, `totalPrice`.
- Константы: UPPER_SNAKE_CASE — `MAX_BOOKING_HOURS`, `BOOKING_STATUS`.
- Функции: camelCase — `calcPrice`, `isSlotAvailable`, `createBooking`.
- Классы: PascalCase — `ValidationError`, `ConflictError`.
- Файлы и каталоги: camelCase для JS-модулей — `bookingService.js`, `asyncHandler.js`
  (исторически сложившееся соглашение проекта; переименовывать файлы нельзя —
  это разорвёт историю git и ~20 импортов). Новые файлы продолжают то же соглашение.
- Таблицы и колонки SQLite: snake_case — `objects`, `total_price`.
- Имена должны отражать назначение. Запрещены `a`, `b`, `tmp`, `data` без уточнения.

## Форматирование

- Отступ: 2 пробела.
- Кодировка: UTF-8, перевод строки LF (закреплено в `.gitattributes`).
- Точка с запятой обязательна.
- Одинарные кавычки в JS.
- Максимальная длина строки — 100 символов.
- Файл заканчивается переводом строки, висячие пробелы отсутствуют.
- **Не более одной команды в строке.** Цикл, объявление и вызов занимают отдельные строки.

## Комментарии и документация

- Каждая публичная функция получает JSDoc: назначение, `@param`, `@returns`,
  `@throws` — если выбрасываются исключения.
- Комментарий объясняет **почему**, а не повторяет код.
- Комментарии ставятся только в неочевидных местах: обход календаря,
  закрывающий транзакцию, границы валидации.
- Закомментированный код и устаревшие комментарии удаляются, а не хранятся.

## Архитектура

- `src/routes` — только HTTP: чтение `req`, вызов сервиса, отправка ответа.
  Бизнес-логики здесь нет.
- `src/services` — вся бизнес-логика и работа с БД.
- `src/db.js` — схема, миграции, сид. Других таблиц не создаёт.
- `src/middleware` — обёртки Express (`asyncHandler`, `errorHandler`).
- `src/public/api.js` — единственное место, где фронтенд обращается к серверу.
- `src/public/ui.js` — форматирование и уведомления, без обращений к сети.
- Модули фронтенда не импортируют друг друга напрямую, кроме `app.js`.
  Связи выполняются через подписки: `map.subscribe({ onSelect })`.
- Изменения данных выполняются в транзакциях SQLite.

## Обработка ошибок

- Свои ошибки наследуются от `ApiError` в `src/exceptions.js`:
  `ValidationError` (400), `NotFoundError` (404), `ConflictError` (409).
- Сервисы **выбрасывают** типизированные исключения, а не возвращают `{ ok: false }`.
  Слой HTTP превращает их в код ответа.
- Фронтенд получает `{ error: 'текст' }` и показывает его через `showToast`.
- Никаких «голых» `catch`: перехваченная ошибка либо обрабатывается,
  либо логируется в консоль, либо превращается в ApiError.

## Безопасность

- Только подготовленные SQL-выражения (`db.prepare`), никакой конкатенации входных данных.
- Валидация входных данных — на сервере, в сервисном слое.
- Фронтенд дублирует только самые простые проверки формы для быстрого отклика.
- Ошибки наружу отдаются текстом для пользователя, стек — только в консоль сервера.

## Git

- Сообщения коммитов на русском, в прошедшем времени, с указанием сути:
  «Исправлена проверка занятости слота», а не «fix».
- Один коммит — одна логическая задача.
- Служебные файлы (БД, логи, node_modules, отчёты покрытия) — в `.gitignore`.
