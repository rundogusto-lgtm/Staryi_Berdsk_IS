# Текст выступления
## Защита проекта «Старый Бердск» (7–10 минут)

## Слайд 1. Титульный (30 сек)
«Здравствуйте! Представляю проект „Старый Бердск“ — веб-систему управления
арендой объектов парка отдыха. Автор: Мариненко Е. Е. Ссылка на репозиторий —
на последнем слайде.»

## Слайд 2. Проблема (1 мин)
«Аренда в парке ведётся вручную: журнал, звонки, цена „на глаз“.
Отсюда двойные брони одного объекта, ошибки в расчётах, нет статистики.
Наше решение — единая веб-система: карта занятости, валидация слотов,
честная цена с сезонным коэффициентом и цифры для директора.»

## Слайд 3. Цель и задачи (30 сек)
«Цель — рабочая система аренды к релизу 1.0. Задачи: интерактивная карта,
бронирование с расчётом цены, панель администратора, дашборд директора,
тесты, документация.»

## Слайд 4. Аудитория (30 сек)
«Три роли. Клиент выбирает объект на карте и бронирует в три клика.
Администратор ведёт статусы: оплата, активация, отмена. Директор смотрит
выручку и печатает чеки.»

## Слайд 5. Функциональность (1 мин)
«Система умеет: показывать 8 объектов трёх типов с занятостью на дату;
бронировать с горизонтом 90 дней и ценой с сезонным коэффициентом —
летом 1.2, зимой 0.8; вести бронь по цепочке статусов до завершения;
печатать чек в формате А4.»

## Слайд 6. Демонстрация (2 мин)
«Показываю живьём. Выбираю беседку на карте — открывается карточка,
цена пересчитывается. Создаю бронь — карта краснеет. В админке подтверждаю
оплату. В дашборде растёт выручка, формирую и печатаю чек.
[Запасной вариант — скриншоты и GIF, если нет сети.]»

## Слайд 7. Архитектура (1 мин)
«Стек: Node.js + Express, SQLite, фронтенд без сборки на ES-модулях.
Сервер: маршруты — только HTTP, бизнес-логика — в сервисах, ошибки —
типизированные исключения 400/404/409. Фронтенд ходит в сеть только через
api.js, экраны связаны подписками через app.js. Детали — в компонентной
диаграмме.»

## Возможные вопросы и короткие ответы
- «Почему SQLite, а не PostgreSQL?» — Ноль настройки, хватает на масштаб
  парка; миграция возможна — SQL стандартный.
- «Почему фронтенд не покрыт автотестами?» — Для проверки DOM нужен
  эмулятор или Playwright. Вместо него написаны 44 тест-кейса, из них
  11 проверяются вручную в браузере. Критичная логика на сервере покрыта
  на 99,5 %.
- «Что будет при двойном клике „Забронировать“?» — Транзакция: проверка
  слота и вставка атомарны, вторая попытка получит 409.
- «Где хранятся данные?» — `data/park.db`, переживают перезапуск.
- «Почему GitHub Pages не заработает?» — Приложение использует SQLite
  и Node.js, а Pages отдаёт только статику. Нужен хостинг с серверной
  поддержкой.
- «Что нашли интеграционные тесты?» — Пустое тело запроса возвращало
  404 вместо 400: отсутствие поля маскировалось под «объект не найден».
