# Стратегия ветвления проекта

## Дата: 2026-10-08
## Проект: «Старый Бердск» — веб-система управления арендой объектов парка отдыха

## Выбранная стратегия: GitHub Flow

## Обоснование
Проект небольшой (1–2 разработчика), без сложного релизного цикла и окружений.
Используем GitHub Flow:
- `main` — стабильная версия, всегда рабочая (`npm test` зелёный);
- `feature/*` — новые функции;
- `bugfix/*` — исправления;
- `release/*` — подготовка релиза (версия, changelog).

## Правила
1. Любая новая функция — в отдельной ветке от актуального `main`.
2. Коммиты — осмысленные, на русском, один коммит — одна задача.
3. После завершения — слияние в `main` (merge, без rebase чужой истории).
4. Конфликт разрешается вручную: открыть файл, найти маркеры `<<<<<<<` / `=======` /
   `>>>>>>>`, выбрать правильный вариант, удалить маркеры, закоммитить.
5. `main` всегда рабочая: перед слиянием — `npm test`.
6. Релиз помечается аннотированным тегом `vX.Y`.

## Разрешённые конфликты

### Конфликт 1: bookingService.js, функция validateBookingInput
- **Ветки:** `bugfix/booking-validation` vs `main`
- **Причина:** учебная тренировка — обе стороны меняли сообщение об ошибке
  превышения вместимости (`validateBookingInput`).
- **Решение:** оставлен вариант с текстом «Превышена вместимость», покрытый
  существующим тестом `validateBookingInput({ ...base(), guests: 9 })`.
- **Проверка:** `npm test` — 40 тестов зелёные.
